For the later daily timeline, handover-version acknowledgements, reviewed timers, three-step help and weekly institution review, see [Everyday interactions](INTERACTIONS.md). Those changes also remain source-only and include an additional table and erasure inventory.

## Implemented behavior

| Area | Behavior |
| --- | --- |
| Home handover | The household selector starts off. Choosing a family requests the latest shared feeding, diaper, sleep and pumping record within seven days, including event time and recorder. No record means unknown. The screen distinguishes the time information was retrieved from the care event's time. Parent records and tracking free text are excluded. |
| Handover notes | Each active member edits only their own note. Saving and sharing are separate choices; sharing starts off. Published notes require a matching current membership revision and are displayed for seven days after saving. Changing permissions/rejoining requires reviewing and saving again before others see a note. The author can still review a recent own note privately. Emptying and saving clears the stored note. These are not AI attachments. |
| Help progress | Each signed-in person can explicitly save preparing/waiting/booked and an optional next-contact time in JST. Calls, link clicks and sheet navigation never change progress. It is private, independent of an institution's actual intake, and sends no reminders. Removed contacts retain a separately labeled history that can be cleared. No health-text field is collected. |
| Service instructions | Staff can publish application steps, preparation and fallback contact instructions, plus active/paused availability and a pause notice. Paused cards suppress the booking action and show the pause/fallback information. These fields are factual operator input; the app does not infer opening hours, eligibility or availability. |
| Account handling | Operators record identity-verification and processing procedure references, completed steps, next action, expected reply time and outcome. Access/deletion completion requires identity attestation and all relevant processing steps. Deletion completion additionally requires a remaining-copy/retention explanation. Finalized results have immutable receipt IDs; stale writes conflict. Private verification/execution references are never returned through the receipt reference lookup. |
| Actionable answers | Sync and worker chat return an opening excerpt, the actual submitted question/selected profile, questions extracted from the already processed answer and retrieved-document source metadata. The complete answer and cautions remain visible. The excerpt is not a second AI summary; no additional model call or inferred clinical facts are introduced. |
| Consultation handoff | A generated answer offers an editable consultation-question draft based on the person's original question. Explicit confirmation opens the existing sheet's incoming review. The person still chooses which question slot to replace. Neither the AI answer nor the draft is automatically sent to an institution. |
| First use | The recording example now walks through an example save, finding it on Home/Records and correcting it. All steps stay in component memory; no tracking or AI request is made. |
| Invitations | Managers can issue a single-use, 24-hour member invitation link and a browser-generated QR code. Only the hash is stored. The bearer secret uses a URL fragment, is removed from the visible URL on capture and stays in memory through initial sign-in. Joining requires an authenticated explicit confirmation and does not enable sharing. The invitation review hides existing family panels without unmounting drafts. Acceptance navigates to the actual invited family, including after first-use onboarding; existing unsaved sharing edits still require confirmation before switching families. New links revoke the same issuer's unused links. Managers can revoke links. Membership/permission revision changes invalidate the issuer's outstanding links. Existing account-ID invitations remain available. |
| Connection failures | Connection notices explain disconnected/reconnected states. Recording distinguishes a client-side unsent operation from an unconfirmed result after dispatch and from saved data. Reconnection refreshes reads, never writes. Existing creation request keys remain stable for explicit retries. Checking saved records does not discard a pending operation. The service worker's legacy queue replay and read helpers are removed; legacy sync events are ignored. No offline queue or new browser health-data storage is introduced. |

## Account execution boundary

The operator screen records **attested manual execution**. It does not reset passwords, issue reset links, invalidate sessions, erase application data or delete backups. A responsible operator must perform these actions through their controlled process before checking the corresponding steps. A checkbox is an attestation, not technical proof of external execution. Requests remain open until actual processing is complete; the application rejects completion without the required attestation, procedure reference and outcome.

Do not enter identity documents, passwords, recovery codes or health content in procedure references or public replies. Public reference lookup exposes only status, public next steps, expected reply and the non-sensitive receipt. No email delivery is introduced. Existing finalized legacy requests can be read but are not assigned invented verification evidence or receipts.

## Source-review fixes

- Auth change notifications distinguish expiry, explicit sign-out, sign-in and cross-tab session changes. Expiry clears private screens/tasks while retaining the pending invitation only in memory. Signing back into the same known account can continue the authenticated review; switching accounts or explicitly signing out clears it. Accepting is still a separate user action. Reloading the page loses the captured invite.
- Recording uncertainty belongs to the original request key. Once a dispatched save is unconfirmed, an offline or rejected retry retains that state until a successful response or explicit abandonment. Restored pending operations are conservatively unconfirmed. Retries reuse the same content, time and key; reconnection never sends a write.
- Help-progress editors are owned by the directory's account-session hook and keyed by contact, including unsaved input for contacts with no server row. Moving a removed contact into the historical section preserves form values, reviewed revision, conflict, save status and in-flight locking. Successful writes and read conflicts update the same editor. Explicit discard clears local input; refresh/close/logout still loses session-only drafts. Removed contacts with no existing saved row cannot create new progress and show that limitation.
- Operator forms register the existing entrance-navigation guard as well as the unload warning. Back/Forward and entrance changes ask before losing edits; pending saves block navigation. Cancel preserves the form and restores tracked browser history. Explicit logout uses the same discard check.

## API and rollout

Deploy the matching frontend, backend and worker together. Existing API startup `create_all` registers five new tables: `family_handovers`, `family_invite_links`, `support_journeys`, `account_workflows` and `account_workflow_events`. This phase adds no columns to existing tables and no dependency. Startup/table creation was not executed. Back up the deployment through its existing process before a later authorized rollout.

- `GET /api/families/{family_id}/overview`, `POST /api/families/{family_id}/handover`: active membership required; own-note writes require note and membership revisions.
- `GET/POST /api/families/{family_id}/invite-links`, `POST .../{link_id}/revoke`: family managers only. Creation/preview/accept are rate limited. Token preview/accept use JSON POST bodies, never query strings.
- `POST /api/family-invitations/preview` and `/accept`: authenticated, explicit bearer-token use. Acceptance atomically consumes the invitation and activates only a member role with empty sharing permissions; already active memberships retain their existing permissions. Retrying consumption by the same still-active member is idempotent while the invitation remains valid.
- `GET /api/support-journeys`, `POST /api/support-journeys/{contact_key}`: authenticated owner only. Contact keys come from published stable resource keys (or `organization`), and writes use revisions. Clearing keeps a revision tombstone to reject old writes.
- `POST /api/admin/account-requests/{reference}`: now requires `revision` and structured workflow fields. Terminal receipts cannot be edited. Admin-only status events are retained without identity documents.
- Sync/personalized chat and `ai_chat`/legacy personalized worker tasks return `presentation`. Streaming continues its existing text behavior. Sources come exclusively from the actual retrieved documents' HTTPS URL metadata, never from source names or model text. Built-in sample documents without URL metadata produce no citation link.

Add the new stores to the manual erasure inventory: own help progress; handover text; issued/consumed invitation metadata; account workflow references, audit events and receipt retention. Published directory instructions remain public. Seven-day note visibility and invitation expiry are access rules, not promises of physical data deletion. A removed institution's saved progress is historical information, not a current contact recommendation.

The v5 service worker never opens or replays the obsolete `postpartum-offline` IndexedDB queue. Privacy settings provide explicit device-wide cleanup of that legacy database, and sign-out/authentication-boundary cleanup also attempts deletion because the old data has no reliable account boundary. Cleanup does not touch current access tokens, display preferences, server records or server drafts. A blocked deletion is reported for explicit cleanup; another tab/old worker may need to release its database connection. No browser queue cleanup was executed in this source-editing session.
