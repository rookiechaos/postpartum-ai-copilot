# UI architecture for families and small institutions

The [shared UI foundation and quieter Home](UI_FOUNDATION.md) adds common controls and design tokens, limits the initial recent-record list, and groups secondary Home tools behind disclosures. Runtime acceptance remains pending.

The subsequent [first-time-use UI refinement](UI_FRIENDLINESS.md) reorganizes Home, correction feedback, AI disclosure/sending, help cards and institution task editing. It has the same source-only execution restriction; the acceptance checks in both guides remain pending.

This phase implements the seven findings from the UI source review. It is **source only**: no application, worker, dependency installation, build, lint, parser, tests, browser, print/QR acceptance, migration or real-data workflow was run. Source inspection and `git diff --check` do not establish that the interface renders or operates correctly.

## State and privacy boundaries

The authenticated family component remains the owner of session-scoped private state. Visited pages remain mounted and hidden pages remain excluded from layout/focus. Logout, account or entrance changes retain the existing teardown behavior. Optional account-bound drafts remain off by default; this phase adds no health information to browser storage.

Focus changes happen after navigation, sending a question, preparing a phone script, choosing a follow-up, previewing publication, or locating an input error. Submitting a question reveals the conversation so progress is visible; a status message announces an available answer. Background refreshes and assistant responses do not call document scrolling or focus. The shared helper opens containing details before revealing the requested field and respects hidden panels. Navigation uses immediate scrolling and preserves reduced-motion styles.

Header and Settings use the same language selector backed by the active i18next display choice. Profile loading and retrying a failed load never apply an older account language to the interface. Language changes update the display immediately and use the existing language-detector cache; only explicitly saving settings writes the current language to the account. If the display language changes during that save, its response does not switch the UI back. Chat keeps one persistent waiting/answer live region; the composer's repeated waiting text is a visual reminder without another live region.

Chat continues to send the current question and only explicitly selected preceding exchange/profile scope. The outgoing question, exchange and profile-choice snapshot is retained in memory while the request is pending. Longer processing-provider/operator notices are expandable and available before consent. This is a presentation change, not a new permission or automatic send. Message text remains escaped React text; no HTML/Markdown execution is introduced.

Phone scripts and consultation review questions still stay in screen memory until explicitly applied. SupportHub does not call a contact, share a sheet, replace an existing question, print or export on navigation. Existing consultation source-version checks and manual sharing choices remain intact.

Support navigation uses a single numbered `{ key, view, question }` request from the authenticated app. A request is consumed once: a contacts request selects and focuses the contacts heading without changing the incoming-question state; only a new sheet handoff updates the review question. Plain menu returns do not send a new request. This also prevents an old script from being reintroduced when returning from contacts to an already edited sheet.

Consultation focus requests are applied after the target is rendered and the sheet is visible. Applying a question focuses its selected textarea; dismissing the review or confirming draft deletion focuses the sheet heading. The shared helper reports success only when focus reaches the target, so a hidden or disabled target does not consume its request. Background refreshes and completion of a sheet request do not create new focus requests. No tab switch clears the sheet's local edits or manual sharing choices.

## Institution validation and publication

`directoryValidation.js` validates all draft contacts before save, and all publication fields before preview/publish. Incomplete draft names/source URLs remain allowed; nonempty URLs, phone/email formats, lengths and dates must be valid in either path. Publication additionally requires institution/contact names and source URLs. The API remains authoritative.

Saving/previewing trims name/URL/email edges, converts full-width phone digits with Unicode normalization and normalizes common phone dash characters. The normalized profile is rendered in the preview and submitted as the same profile. Checking errors alone makes no network write. A failed save preserves the local profile.

For server 422 responses, the API client retains only validation paths and codes, excluding raw request values and validation messages. Known directory field paths map to localized messages and focus targets. Unknown errors use a localized form-level message. Existing authentication-generation checks still precede response acceptance. Workspace revisions, reload guards, explicit publication preview, history restoration and unsaved-navigation handling are unchanged.

Successful publication shows a result region with an action to expand and reveal the current published directory. The preview's bottom button can disappear without losing the next focus target: a publication focus request is processed after the result renders and editing is unblocked. If focus stayed on the original control or returned to the document body, it moves to the result; moving to another control while waiting cancels that automatic move. Initial loads and other background work do not create this publication focus request.

This phase introduces no new dependency, endpoint, database schema or migration. Earlier product-polish deployment requirements still apply. Publishing this source revision to GitHub does not deploy services or complete the pending acceptance checks.

Returning to the sheet must not reapply the old incoming question. With keyboard navigation, apply each question slot, dismiss a review and delete a draft; focus must reach the corresponding textarea or sheet heading without waiting for unrelated requests.

The relevant contact/section must open and the field must receive focus with a localized description. Cover empty drafts, HTTPS/credentials/port validation, phone normalization, email/length/date limits, future JST checked dates and unknown server 422 errors.
6. Confirm sticky actions do not cover fields/errors on narrow/short screens, preview shows normalized values, publication still requires explicit review, and each edit invalidates that review. Move focus to the language selector while publication is pending and confirm the result does not steal it back. 7. Later run the relevant build and regressions, adjusting fixtures that assert old markup/selectors or API error-helper internals. This document records intended contracts, not successful acceptance results.
