# Product polish for households and small institutions

This implements the next seven requested product improvements. All work is **source only**. No dependencies were installed; no application, worker, migration, build, tests, scanner, browser or real-data workflow was run. The descriptions below are implementation contracts and pending acceptance criteria, not observed results.

## Save and draft contracts

Record creation accepts an optional `request_key` UUID, required by the new UI for retryable writes. With a key, an explicit timestamp is required. A receipt and the new record commit in one transaction. `(user_id, request_key)` is unique and stores a content hash plus response metadata, without duplicating health notes in the receipt. Replays with identical content return the original result, changed content returns 409, and a request whose record was deleted returns 409 instead of recreating it. A receipt's record identity is checked before returning it, protecting against numeric ID reuse. Legacy internal creation paths without a key retain their existing behavior. Update/delete still require immutable identity and revision; repeated updates cannot create duplicate records.

`/api/drafts` always binds identity to the authenticated user. Preference revisions and draft revisions are compare-and-swap preconditions. The preference predicate is checked in the write itself; PostgreSQL also locks the preference row so disabling cannot race with an in-flight draft write. Clearing/expiring a draft erases its content while retaining a monotonically increasing revision marker, preventing a stale page from overwriting a newly started draft in the same slot. Disabling recovery erases all of that account's draft rows and advances the preference revision. Old requests cannot revive them after re-enabling.

Drafts are server-side account data, not medical text stored in localStorage. Draft status distinguishes current unsaved changes from confirmed saves, including edits made while an earlier save was in flight. Emptying the visible input does not silently erase an earlier saved draft; the delete action remains available. Signing out/account changes destroy mounted screen memory; the API client's existing authentication-generation checks invalidate old responses. Same-account token refresh continues existing work. Account-bound saved drafts remain available after signing in again until disabled, cleared or expired. Recovery is not offline record saving, guaranteed delivery of the latest keystroke, full chat-history sync or AI-task resumption.

Draft storage has a 32,000-character JSON bound per kind. Keep actual deployment backups and retention in mind: erasing a live field does not remove historical backup pages or downloaded copies. No stronger deletion guarantee is introduced here.

## Sharing and external processing

`include_previous` grants context only when it is boolean `true`. Client context has fixed question/answer fields rather than arbitrary message roles. The backend and worker validate bounds, and the AI service checks the combined input before provider processing. Previous assistant text is treated as unverified AI output. Profile attachment stays a separate, default-off choice. Follow-up selection is removed after a successful reply; recovery never silently restores consent.

Family membership alone grants no record categories. Baby records, parent records and free-text notes have distinct booleans. Family reads are restricted on both the route and service to at most the last seven rolling days, including direct API calls; local daily/weekly summaries use that same boundary. Existing legacy `share_tracking` state does not silently opt members into the new granular contract; owners must make a new selection. Explicitly setting `share_tracking=true` now selects baby records only and requires the current member revision like every other sharing write. Names/account identifiers are not automatically attached to AI through family sharing. Family summary endpoints now summarize only the selected shared records locally and no longer invoke an unscoped private AI summary. Legacy family tasks are not exposed in this UI.

Re-invitation clears earlier sharing permissions. Member revisions increase on invitation, acceptance, decline, revocation, leaving and each sharing change. Sharing writes require the revision that the client actually reviewed; a delayed request from an earlier membership or earlier sharing setting returns 409, including after re-joining. The UI preserves unsaved choices on conflict, pauses saving, and requires an explicit reload before new selection. Acceptance also compares the queried pending membership revision before activation. Revocation and leaving deny later shared-data requests; the visible shared panel refreshes on focus and every 30 seconds. Information already received, copied or downloaded cannot be recalled. Institutions gain no household access through directory-editing permissions.

## Database and rollout

New tables registered in `backend/models/database.py` are created by the existing API `init_db()` mechanism when later authorized to start:

- `tracking_writes`: durable creation receipts, including after the associated record is deleted.
- `draft_preferences` and `user_drafts`: recovery choice, bounded working content and revision markers.
- `directory_workspaces` and `directory_history`: a saved public-information draft and publication snapshots.

The existing tracking identity migration also adds `family_members.revision` with an initial value of 1 and installs a unique `(family_id, user_id)` index for family memberships. If an old database contains duplicate memberships, index creation fails rather than silently merging permissions or deleting rows. Inspect and resolve those duplicates through an authorized migration procedure before rollout. Existing record identities/content and family permissions are not silently reassigned.

Institution GET initializes the staff-only workspace from the existing public profile once. Previously published information is seeded as history. Public `/api/pilot` continues to return only the published profile, never the draft/history. New metadata is additive to public contact JSON. Draft URLs may be empty, while publication requires valid source URLs and nonempty institution/contact names. Workspace revisions protect draft save, publication and restoration from concurrent overwrites.

Institution mutation bodies now contain `{ profile, revision }`; restoration uses `{ history_id, revision }`. Family sharing bodies require the `revision` returned by the member list, and shared-data `days` accepts only 1–7. Deploy frontend and backend together. Back up the actual deployment, validate fresh/existing SQLite and PostgreSQL initialization, and start workers only after API initialization completes. None of these operations was executed here. Existing regression fixtures may need updates for new schema fields, translations, component imports and the changed family-summary contract.

The manual account-erasure inventory must now also include record receipts, draft preferences/content, family memberships/groups and any applicable institution draft/history attribution, alongside the stores in PRODUCT_IMPROVEMENTS.md. This remains an operator procedure, not an automatic erasure executor. No new frontend dependency was added in this polish phase.
